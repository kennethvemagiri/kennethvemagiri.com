LLM observability in production: traces, costs, and SLOs

Demos log the final string. Production needs span-level visibility: retrieval time, prompt tokens, cache hits, provider errors, and budget alarms—without turning your datastore into a PII warehouse.

Kenneth Vemagiri · ~7 min read · April 2026

  • Production
  • LLM
  • SRE

1. One trace per user request

I give each HTTP request a trace ID and nest spans: retrieve, rerank, llm_first_token, llm_complete, post_validate. That breakdown is how you learn whether latency is search-bound or generation-bound.

2. Log structure, not raw text—by default

Payloads often contain personal data. I store hashed prompts, token counts, retrieved chunk IDs, model name, temperature, and finish reason. Full text replay stays in encrypted short-retention buffers only when compliance signs off.

3. Cost and token budgets

I emit per-request prompt_tokens and completion_tokens to metrics with labels for route and tenant. Alerts fire on sustained p95 growth after deploys—that is how runaway context stuffing gets caught early.

4. Error taxonomy

Provider timeouts, rate limits, content-filter blocks, and tool validation failures should be typed errors in your API layer—not a generic 500. Dashboards split retryable from user-fixable failures.

5. SLOs you can defend

Examples: “p95 end-to-end < 4s for FAQ route,” “> 99% tool arguments pass schema validation,” “zero cross-tenant chunk IDs in traces.” Tie releases to those SLOs the same way you would for payments or auth.
