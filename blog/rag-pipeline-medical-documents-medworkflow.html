How I built a RAG pipeline for medical-adjacent documents

When you sell AI-powered websites and chat to UK healthcare practices, patients don’t want clever prose—they want answers grounded in that clinic’s opening hours, fees, and policies. Here’s how I approach RAG so the model cites the practice’s own documents instead of improvising.

Scope & safety This post is about informational workflows—opening times, registration, parking, pricing summaries the practice already publishes—not diagnosis or treatment. Outputs should carry clear disclaimers, route urgent cases to human staff, and follow UK GDPR, your DPIA, and the practice’s own governance. Nothing here is medical advice.

1. The problem: generic chat won’t survive contact with a GP reception desk

MedWorkFlow targets UK clinics that need professional web presence and a patient-facing assistant. A plain LLM will happily sound authoritative while simultaneously inventing a phone number or merging two policies from different branches. For this market, faithfulness beats fluency. Retrieval-augmented generation (RAG) is the default pattern: retrieve grounded passages, then ask the model to answer only from what it was shown.

2. System shape

I treat the stack as four bounded services with clear contracts:

  1. Ingestion — turn PDFs, HTML, and admin uploads into normalised text + metadata.
  2. Indexing — chunk, embed, and write to a vector index (often with a metadata filter per practice_id).
  3. Query path — embed the user question, retrieve top‑k chunks, optionally rerank, then assemble a cited prompt.
  4. Policy layer — PII redaction in logs, rate limits, refusal templates, and human handoff when confidence drops.
# Conceptual flow (not a single script—usually separate workers + API)
upload → parse (pdfplumber / unstructured) → clean → chunk
     → embed (e.g. text-embedding-3-small or open local model)
     → upsert(vector_db, namespace=practice_id)
query → embed → retrieve(k=8) → optional_cross_encoder_rerank(k=4)
     → build_prompt(snippets + "cite source IDs") → LLM → post-check

3. Ingestion: don’t lose structure

Clinic PDFs often mix paragraphs, bullet lists, and tables (fee schedules). If you flatten everything into one blob, chunk boundaries slice through tabular rows and the retriever returns nonsense halves. I keep document structure hints in metadata: page number, heading trail (H1→H2), and whether a block came from a table. Libraries like Unstructured or careful pdfplumber extraction get you most of the way; the rest is heuristics you tune per customer.

4. Chunking: optimising for recall on short factual questions

Patients ask:“Are you taking new NHS patients?” “Do you charge for sick notes?” Those map to small, dense passages. I typically use:

  • Target size ~300–600 tokens with ~15–20% overlap so split sentences aren’t orphaned.
  • Respect boundaries — prefer breaks at headings and paragraph ends.
  • De-duplication — boilerplate repeated footers inflate retrieval; hash-normalise or strip repeated legal blocks.

For FAQ-style pages, I sometimes build one chunk per Q/A pair if the HTML structure allows—retrieval becomes eerily precise.

5. Embeddings & vector store

For multilingual patient bases, I pick an embedding model known to handle British English clinical-adjacent vocabulary well and keep it frozen per index version so you can reproduce results. In the vector DB, every vector carries metadata: practice_id, doc_id, section_title, source_url, and compliance flags (e.g. internal-only vs public).

Hard filter first — always constrain retrieval to the tenant. Cross-tenant leakage is a career-limiting bug.

6. Retrieval: k is not “set and forget”

I start with k=8 dense retrieval, then either:

  • compress to top 3–4 with a small cross-encoder reranker, or
  • use hybrid search (BM25 + dense) when the query contains rare tokens like drug names or postcode fragments.

If nothing clears a similarity threshold, the product shouldsay “I don’t have that in the documents you gave me” rather than letting the LLM fill the gap.

7. Prompting with citations

The system prompt I use is deliberately boring: answer in plain English, quote only from the provided snippets, and append something like [doc:title § section] for each claim. I reject answers that reference facts not present in the context—either by a light validator (regex / simple entailment check) or by asking the model to output JSON with claims[] mapped to snippet IDs and dropping unmapped claims.

8. Guardrails beyond the model

  • Input — block obvious prompt-injection patterns; trim absurd context stuffing.
  • Output — scan for “book an appointment” flows and ensure they deep-link to real booking URLs from metadata, not invented paths.
  • Urgent language — escalate chest pain, self-harm, or emergency keywords to a static crisis message + human routing.
  • Logging — store prompt hashes and snippet IDs, not raw patient narratives, unless contracts explicitly allow it.

9. Evaluation (the part that separates a demo from a product)

I hold out a small set of question–answer pairs per practice, labelled by staff—“ground truth” strings straight from their published material. Offline metrics:

  • Context precision — did the retriever surface the right chunk?
  • Citation accuracy — does each sentence map to a retrieved span?
  • Abstention rate — when there is no answer, does the bot refuse instead of hallucinating?

Regression-test those suites whenever you change embedding model, chunk size, or prompt.
