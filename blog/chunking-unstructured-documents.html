Chunking unstructured documents without wrecking retrieval

Bad chunking is the silent killer of RAG demos. These are the rules I apply before I touch an embedding model.

Kenneth Vemagiri · ~7 min read · April 2026

  • RAG
  • NLP
  • Data

1. Preserve headings in metadata

When I split text, each chunk carries a heading path (e.g. “Fees → Private patients”). Retrievers can display that path to users and models use it as free structure. Flattening the document into a string throws that signal away.

2. Tables need special treatment

Row-level splits produce useless vectors (“£45” with no column header). I either keep small tables as a single chunk or linearise them with explicit column names per row. For wide sheets I chunk by logical row groups, not token count alone.

3. Token windows vs semantic boundaries

Fixed-size windows with overlap are a decent baseline. When quality plateaus, I experiment with SemanticChunker-style splits: break when cosine distance between sentence embeddings spikes. The cost is extra API calls offline—not on every query.

4. Overlap is cheap insurance

Fifteen to twenty percent overlap between consecutive chunks cuts down edge cases where the answer sits on a boundary. I measure retrieval hit-rate before and after; the storage cost is usually negligible next to re-embedding everything.

5. Deduplicate boilerplate

Headers, footers, and repeated disclaimers dominate similarity search if they appear in every chunk. I strip or down-weight them once per document version so the index reflects the unique facts.
